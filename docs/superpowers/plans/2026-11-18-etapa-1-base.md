# Etapa 1 — Base del proyecto (backend Agenda de citas) · Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Backend funcionando con las 9 tablas migradas, seed de datos, autenticación JWT con refresh y roles, y la matriz de roles probada contra PostgreSQL real.

**Architecture:** Fastify 5 + TypeBox (validación) + Kysely (queries) sobre PostgreSQL local; módulos por dominio (`routes` + `service`); node-pg-migrate con up/down; Vitest unitario + integración con BD real. Errores con envelope único y `requestId`.

**Tech Stack:** Node 22 ESM · TypeScript strict · fastify ^5.12.6 · @sinclair/typebox ^0.34 · kysely ^0.29.8 + pg ^8 · argon2 ^0.45.2 · @fastify/jwt ^10.2.5 · @fastify/cookie/cors/helmet/rate-limit/swagger(-ui) · node-pg-migrate ^9.0.0 · tsx · Vitest · ESLint + Prettier.

**Spec:** `docs/superpowers/specs/2026-11-07-agenda-citas-backend-design.md` (DDL de las 9 tablas en §5; endpoints de auth en §6) · `docs/SEGURIDAD-STACK.md` (vinculante) · `Agenda_citas.md` (reglas de negocio).

**Nota de alcance:** el registro público de pacientes y la vinculación por cédula/teléfono se incluyen aquí (módulo auth completo; las tablas ya existen). Sin nodemailer, sin cron, sin disponibilidad — etapas posteriores.

## Global Constraints

- `"type": "module"`; `"engines": { "node": ">=22.0.0" }`; TypeScript `"strict": true`.
- Versiones floor (no negociable): fastify `^5.12.6`, @fastify/jwt `^10.2.5`, kysely `^0.29.8`, node-pg-migrate `^9.0.0`, argon2 `^0.45.2`, pg `^8`, typebox `^0.34`.
- JWT: `expiresIn` SIEMPRE número de segundos — access `900`, refresh `7 * 86400 = 604800`. Un solo secreto global por tipo de token; prohibido key por-request. Secretos distintos para access y refresh (dos plugins @fastify/jwt con namespace o dos instancias de verificación manual — ver Task 9).
- Cookie refresh: `httpOnly`, `secure: env.cookieSecure`, `sameSite: 'strict'`, `path: '/api/v1/auth'`. En BD solo `sha256(token)` hex; token claro jamás se loguea ni persiste.
- Roles exactos: `'paciente' | 'admin' | 'recepcion'`. Estados de cita: `'pendiente' | 'confirmada' | 'atendida' | 'cancelada' | 'no_asistio'`. Orígenes: `'web' | 'recepcion'`.
- Errores: `{ error: { code, message, details?, requestId } }`; éxito: `{ data }`. Mensajes en español.
- `trustProxy: false`. Rate limit global 120/min; login 5/min; registro 5/min; refresh 10/min.
- Contraseñas: argon2id (defaults de la librería), mínimo 8 caracteres.
- Zona: guardar UTC; helpers de tiempo con `Intl` y `America/Guayaquil`.
- SQL: solo parametrizado (Kysely / `sql\`\``). Prohibido `Kysely<any>` fuera del provider de migraciones si existiera (aquí: prohibido).
- CI gate: `npm audit --omit=dev --audit-level=high` rompe el build. Lockfile `package-lock.json` commiteado; CI con `npm ci`.
- Commits convencionales: `feat:`, `test:`, `chore:`, `docs:`, `fix:`.

## Review Focus

1. **Refresh token reutilizado (replay)** — un refresh ya revocado debe revocar TODAS las sesiones del usuario y responder 401; probado en Task 9.
2. **Email duplicado en registro** — debe responder 409 `DUPLICATE_VALUE`, nunca 500; probado en Task 9.
3. **Usuario inactivo intenta login** — 401 con el mismo mensaje que contraseña incorrecta (sin filtrar existencia de cuenta); probado en Task 7.
4. **Access token sin `exp`** — imposible: TTL como segundos; la prueba decodifica el token y exige `exp` ≈ `now + 900`; probado en Task 9.
5. **`migrate down` + `up` idempotente** — el down de cada migración debe dejar la BD en el estado previo sin errores; probado en Task 6.

### Task 7: Servicio de autenticación

**Files:**
- Create: `src/modules/auth/auth.service.ts`
- Test: `tests/auth-service.test.ts` (integración)

**Interfaces:**
- Consumes: `db`, tipos (Task 5), `AppError` (Task 3), `env` (Task 2).
- Produces (clase `AuthService`, todas async):
  - `hashPassword(plain: string): Promise<string>` / `verificarPassword(plain, hash): Promise<boolean>` (argon2).
  - `registrar(input: RegistroInput): Promise<{ usuarioId: number; pacienteId: number }>` donde `RegistroInput = { email; password; nombres; apellidos; cedula?; telefono; fechaNacimiento?; aceptoPrivacidad: boolean }` — rechaza si `!aceptoPrivacidad` (`badRequest('CONSENTIMIENTO_REQUERIDO', ...)`); en UNA transacción inserta usuario (rol `'paciente'`) + paciente, y si `cedula` o `telefono` matchean un `pacientes` con `usuario_id IS NULL`, vincula ese registro en vez de crear uno nuevo (UPDATE `usuario_id`); email duplicado deja que PG lance 23505 → traducido en Task 9 a 409.
  - `login(email, password, meta: { ip?; userAgent? }): Promise<{ accessToken; refreshToken; usuario: UsuarioPublico }>` — `UsuarioPublico = { id; email; nombre; rol }`; usuario inactivo o contraseña incorrecta → mismo `unauthorized('CREDENCIALES_INVALIDAS', 'Credenciales inválidas')`.
  - `refresh(token: string | undefined, meta): Promise<{ accessToken; refreshToken }>` — token ausente/inválido/expirado → 401 `REFRESH_INVALIDO`; si el hash existe pero `revocada_en IS NOT NULL` (replay): revoca TODAS las sesiones activas del usuario y 401; rota: inserta nueva sesión, revoca la anterior.
  - `logout(token: string | null, usuarioId: number | null): Promise<void>` — revoca la sesión si existe.
- Tokens: access = JWT firmado con `env.jwtAccessSecret`, `expiresIn: env.accessTokenTtlS` (número), payload `{ sub: usuarioId, rol }`; refresh = `randomBytes(32).toString('base64url')`, se persiste `sha256` hex con `expira_en = now + env.refreshTokenTtlS`.
